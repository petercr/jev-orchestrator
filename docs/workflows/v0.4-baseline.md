# v0.4 offline workflow baseline — protocol v1

This baseline starts v0.4 implementation against the v0.3.1 runtime at
`c9b85b7c5934c3132952bd176e393343dc12c3ae` (PR #50 merged). It changes no
runtime behavior, permissions, thresholds, or budgets. Historical
[issue #31](../benchmarks/issue-31.md) and
[v0.3 decision](../benchmarks/v0.3-decisions.md) fixtures/results remain unchanged.

Run it without credentials, dependency installation in the fixtures, network
access, or installed coding workers:

```bash
pnpm exec vitest run src/orchestration/workflows.test.ts
```

The [executable fixtures](../../src/orchestration/workflows.test.ts) define
three frozen tasks, initial source/tests, and predetermined worker patches.
Each run creates a temporary Git repository, reads its exact simulated public
issue and real `AGENTS.md`, approves implementation, refreshes the repository,
runs independent checks, and reviews acceptance. The initial index, package
scripts, lockfile, and instructions are preserved. Temporary repositories and
their traces are removed after each case.

HTTP and worker processes are simulated at their boundaries. The evaluator,
provider normalization, policy, candidate selection, approval resolution,
execution layer, worker adapters, inspection, metrics, and JSONL writer are
real. Validation launches actual `npm run test` (`node --test label.test.mjs`)
and `npm run lint` (`node --check label.mjs`) processes. The runner refuses
other process commands. Git setup and inspection also run locally.

The suite uses synthetic, explicitly scripted provider answers and test-only
approval callbacks. These callbacks are not available to live runs. No live
assessments or provider/worker quality measurements are collected. Historical
reports retain their original observations; their aggregate findings are not
converted into invented recorded assessments. Passing these cases establishes
enforcement behavior under supplied recommendations, not better model routing.

## Frozen tasks

All tasks require `npm test` and `npm run lint`, a single permitted worker,
default Codex networking off, separate approvals, and task acceptance review.
Source and regression tests are in `label.mjs` and `label.test.mjs`.

| Task | Acceptance criteria | Scripted implementation |
| --- | --- | --- |
| `short-label` | Preserve strings of length 0–10; shorten longer strings to their first 10 characters plus `...`. Add empty, short, and exact-boundary regression cases. | Replace unconditional shortening with a length guard and add the regression cases. |
| `label-fallback` | Add an optional fallback for empty strings, defaulting to `(empty)`; support a custom or explicitly empty fallback; preserve existing shortening. | Add the fallback argument and regression cases. |
| `short-label-repair` | Same acceptance criteria as `short-label`. | First patch incorrectly uses `< 10`; independent tests fail at the boundary. The approved second patch uses `<= 10`, followed by fresh test and lint approvals. |

Three fixture-integrity tests first pass the original tests on the original
source, demonstrate that the new regression fails on that source, and check
each supplied patch. The intentionally incomplete repair patch must fail;
only its final patch may pass. A worker's success exit status is insufficient
to establish task acceptance or independent validation.

Repair handoff assertions check the structured validation generation, script,
exit status, bounded assertion diagnostics, and remaining worker calls. Node's
test-report wording varies between supported versions; those assertions use
the failure evidence carried into the actual worker request.

Freeze these definitions for routing comparisons. Change the protocol version
and explain deviations if task source, acceptance, checks, or scripted patches
must change. Variants below deliberately change preparation, required context,
or process outcomes to exercise a specific boundary; they are labeled separately
from the three complete task workflows.

## Matrix and baseline results

Each workflow and boundary case runs through all six routes with both explicit
worker selections: TypeSafe/Jev, Vercel/Jev, OpenRouter/Jev,
OpenRouter/`openai/gpt-6-luna-decisions`, Cloudflare/Clef, and
Cloudflare/Clef-flash. Synthetic credentials and envelopes exercise the actual
transport boundaries; every request is checked against its fixed endpoint and
bound model. Excluded worker alternatives stay unavailable.

There are 183 tests: 36 complete task workflows, 144 boundary/interaction
cases, and three fixture-integrity checks. The table describes asserted
outcomes for each provider/worker pair, not observed frequencies in real tasks.

| Case | Iterations | Terminal outcome | Independent evidence / interaction |
| --- | ---: | --- | --- |
| Bug fix or feature | 6 | `finished` | One worker; two passing checks; six approvals. |
| Controlled repair | 8 | `finished` | Two worker calls; one failed check followed by two fresh passing checks; eight approvals. |
| Low-confidence worker, then redundant `RUN_TESTS` | 6 | `finished` | Two manual alternatives, each reviewed again; six approvals and eight approval requests. Confidence stays unchanged; no redundant check executes. |
| Invalid evaluation after implementation | 7 | `finished` | One explicit recovery consumes an iteration; six action approvals; two independent checks. Failure records contain no approval or execution. Bound model, worker, and budgets remain intact. |
| Unavailable issue, blank clarification, then typed stop | 3 | `stopped` | Two approvals and one clarification wait; no worker or validation; no fabricated issue or clarification evidence. |
| Passing baseline validation before implementation | 8 | `finished` | Four checks total; the worker invalidates generation 0 and both checks must pass again in generation 1. |
| Repair with one additional required instruction read | 8 | `iteration_limit`, exit 1 | Final patch passes both checks, but no acceptance iteration remains. Two worker calls and partial edits/evidence are retained. |
| Two independently failed patches | 7 | `stopped` | Two worker calls and two failed checks; a third call and completion are unavailable; no transfer to the excluded worker. |
| Missing runnable check / omitted task requirements | 6 | `stopped` | Detected test and lint pass, but completion stays unavailable. Summary retains pending checks and, when applicable, the omitted-requirements flag. |
| Worker failure, timeout, or malformed process result | 4 | `stopped` | Saved edits survive refresh; validation is invalidated; no false completion or automatic retry. |
| Cancellation during the approved worker | 3 | `stopped` | Execution-boundary abort retains edits and failed/cancelled evidence; no later evaluation, validation, or completion. |

The existing [provider matrix](../../src/ai/providers.test.ts),
[orchestration cancellation tests](../../src/orchestration/cancellation.test.ts),
[process tests](../../src/process.test.ts), and
[CLI cancellation tests](../../src/cli.cancellation.test.ts) continue to cover

## Reproduced stops and ownership

| Reproduction | Owning layer | Next permitted choice / next v0.4 investigation |
| --- | --- | --- |
| Worker confidence below the existing threshold | Provider assessment → policy | Stop, request context, or choose and approve an allowed worker manually. Step 2 should show the recommendation and policy override separately. Whether live models still require this detour needs fresh observations. |
| `RUN_TESTS` after every required check passed | Policy → acceptance review | Select `FINISH`, then approve the resolved acceptance review. Existing behavior avoids another check; step 2 should make that choice clear. |
| Invalid evaluation after a patch | Provider contract → explicit recovery | Stop or continue within the remaining iterations. Show the failed attempt separately from action approval. Never normalize an invalid distribution into a usable recommendation. |
| Issue context unavailable or blank | Preparation → user context | Supply actual acceptance criteria through approved clarification or stop. Blank input leaves the preparation gate closed. |
| Required check absent from scripts, or requirements omitted | Validation bookkeeping → candidate selection / policy | Obtain enough task/repository context to resolve the missing requirement or stop. Passing available checks cannot authorize completion. |
| Repair plus another instruction read requires nine actions | Loop iteration bound | Preserve the accepted patch and explain that the run ended without acceptance review. This is a reproduced budget constraint, not authorization to skip a read/check or raise the limit. |
| Both calls to the selected worker consumed | Candidate selection → final approval enforcement | Inspect/request context or stop; no third call, worker switching, or budget reset. |
| Interrupted or failed worker left edits | Execution → inspection / validation generation | Review saved edits and separately approve fresh validation if continuing in-process; traces cannot resume execution. |

No deterministic enforcement defect was found in these scripted sequences.
They reproduce bounded stops and manual routing behavior to give step 2 stable
examples for clearer operator messages. Claims about missed worker routing,
repeated preparation, or improved live completion remain hypotheses until
supported by new observations. Do not tune confidence, prompts, or budgets
from scripted success counts.

## Reserved task for later verification

Reserve `stable-tags` from routing development. It is intentionally absent
from the baseline's recommendation scripts and passing workflow examples.
Use it only after the v0.4 routing candidate is frozen, under the separately
authorized live comparison protocol.

Initial `tags.mjs`:

```js
export const tags = (value) => value.split(',');
```

Task: trim comma-separated tags, remove empty entries, and remove duplicates
while preserving first occurrence order and case. Inputs are strings; no new
dependencies or input-type expansion. Required acceptance examples:

| Input | Result |
| --- | --- |
| `a,b` | `["a", "b"]` |
| ` a, ,b,a,, ` | `["a", "b"]` |
| empty string | `[]` |
| `A,a,A` | `["A", "a"]` |

Allow edits only to `tags.mjs` and a new `tags.test.mjs`. Freeze a repository
with the same instruction and Git setup, `test: node --test tags.test.mjs`,
and `lint: node --check tags.mjs` before live collection. Record its revision,
task/check hashes, installed CLI archive, and actual worker configuration in
that protocol. Acceptance and completed approval loops must be reported
separately; the offline baseline provides no live performance or cost estimate.
