# v0.4 routing explanations

The second v0.4 slice adds plain, grouped explanations to orchestration review,
evaluation recovery, and terminal results. It uses the
[offline workflow baseline](v0.4-baseline.md) to exercise reporting alongside
the existing enforcement layers. No terminal library is added in this slice.

## Reading an action review

Each approval review separates five things:

1. **Model recommendation:** requested action, exact choice/confidence values,
   task-completion/information/testing/stuck probabilities, provider/model
   attribution, and distribution.
   Missing confidence is reported as unavailable; no value is inferred.
2. **Policy decision:** the selected action, override status, and policy reason.
3. **Candidate review:** the action that could actually be resolved, its tool
   and parseable parameters, and any candidate blocker. A manual alternative
   is identified separately from the original policy selection.
4. **Current evidence and limits:** issue/clarification provenance, unread
   instructions, current-generation check outcomes, bounded failure evidence,
   worker limits/selection, remaining iterations, and interaction counters.
5. **Operator choices:** the loop's allowed action names and how to review,
   approve, reject, stop, provide context, or confirm task acceptance.

The allowed names are choices to resolve and review. Selecting a name can
still produce a blocked candidate; it never approves execution. The displayed
parameters retain their existing JSON representation, with secrets redacted
and terminal control bytes escaped. Explanatory strings and check lists are
bounded and rendered as plain lines.

Example excerpt: a low-confidence worker recommendation after preparation.
The complete review also prints attribution, distribution, and parameters.

```text
Iteration 3 of 8 (6 remaining, including this iteration)
Model recommendation
Evaluator requested: CALL_CODEX
Choice probability: 1; reported confidence: 0.1.
Task-completion probability: 0.02.

Policy decision
Policy selected: ASK_USER (override)
Reason: The next-action distribution is too ambiguous for autonomous execution.

Candidate review
Resolving policy selection: ASK_USER.
Safe candidate: ASK_USER

Current evidence and limits
Independent checks (generation 0): test: pending, lint: pending.
Worker calls used: Codex 0/2; Claude 0/2.
Interaction totals: 2 action approvals; 0 manual alternatives; 0 explicit evaluation recoveries.
```

If the operator selects `CALL_CODEX`, its next review says:

```text
Manual alternative requested: CALL_CODEX; original policy selection: ASK_USER.
Safe candidate: CALL_CODEX
```

It still shows the original recommendation and confidence. Execution requires
approval of that resolved candidate. If the candidate cannot be offered, the
review instead names the unavailable action and prints the candidate reason.

## Baseline cases and operator choices

| Situation | Explanation | Operator choice |
| --- | --- | --- |
| Linked issue or instructions not read | Shows the requested worker, preparation policy override, exact resolved read, and remaining unread instruction names. | Review and approve the read, choose another listed action for review, or stop. |
| Issue unavailable / blank clarification | States that operator task context is still required. Accepted replacement context is attributed to clarification. | Approve `ASK_USER` and supply acceptance criteria, or stop. |
| Missing or low routing confidence | Shows the reported confidence exactly, or `not reported`, alongside the policy override. | Supply context or select a listed alternative and separately approve its resolved candidate. |
| Independent validation failed | Names failed/pending checks in the current generation and displays bounded, redacted failure diagnostics. | Diagnose through a listed read/worker/context action and review the resulting candidate. An unchanged failed candidate may remain unavailable. |
| Worker returned failure, timeout, or partial work | Reports the unsuccessful attempt, retained call usage, and fresh validation requirements. | Review saved edits and obtain separately approved independent validation. |
| Prior checks are stale | Names the new generation and explicitly says older results cannot cover its pending checks. | Review the pending independent check candidate. |
| Required check absent / context omitted requirements | Shows missing runnable coverage or the omitted-requirements blocker. Passing detected checks does not clear it. | Obtain enough task/repository context to resolve the missing requirement, or stop. |
| Package manager unknown / inspection refresh failed | Names the specific validation or inspection blocker. | Provide approved context/recover inspection or stop. |
| Worker call limit reached | Separates the confident recommendation, policy selection, and unavailable candidate; names the exhausted limit and fixed worker selection. | Choose an offered inspection/context action or stop; no additional worker call is granted. |
| All checks passed, model repeats tests | Explains the policy-owned acceptance review and identifies a manual `FINISH` selection separately. | Select `FINISH`, review it, and approve only if the original task acceptance criteria are met. |
| Evaluation failed | No candidate/approval is attributed to the failed evaluation. Shows retained checks/call usage and iterations available for explicit recovery. | Enter `continue` for a fresh evaluation or `stop`; continuation consumes another iteration and grants no action approval. |
| Budget ended after a validated repair | States that independent checks passed but completion approval did not fit within the iteration budget. | Review the saved patch/checks/trace. A separate invocation is a new run with its own approvals. |
| Typed stop or interruption | States that the run ended without claiming completion and preserves edits/evidence. Signal exits identify interruption. | Review saved work and diagnostics before explicitly starting another run. |

Action approvals, manual alternatives, and explicit evaluation recoveries have
separate counters during review and in the final summary. Choosing an
alternative is not counted as approving it. Evaluation failure/recovery is
separate from action approval. Passing validation and approved task acceptance
remain separate outcomes.

## Reporting and compatibility boundary

The loop supplies a copied, display-only `ApprovalContext.review` snapshot
with review provenance, the actual iteration limit, and existing metric counts.
It is never read by policy, candidate selection, final approval enforcement,
or execution. It cannot grant permissions or replenish any budget.

Decision-only JSON remains schema v1; orchestration traces remain schema v2.
The snapshot is absent from AgentState, approved candidates, worker context,
and traces. Existing summary metrics remain the reporting source. Traces
remain diagnostic data and cannot be used to resume a run.

The existing workflow suite renders every review/result and checks that
reporting leaves its inputs unchanged across all six model routes and both
workers. Focused presentation tests cover the blockers above, exact confidence,
manual alternative resolution, escaped/redacted parameters, bounded lists,
and reporting snapshots that cannot alter real metrics or iteration limits.

Run the focused checks with:

```bash
pnpm exec vitest run src/cli/presentation.test.ts src/cli.test.ts src/cli.cancellation.test.ts
```

The complete verification gate remains `pnpm check`, `pnpm test`, and
`pnpm build`, using Node 22 or newer. These are offline enforcement/presentation
checks; they do not measure live model routing quality.
