# v0.4 repair routing candidate

This candidate fixes one deterministic detour in the testing-priority rule.
It uses a labeled variant of the frozen `short-label-repair` task from the
[offline baseline](v0.4-baseline.md). Task source, acceptance criteria, worker
patches, checks, and the original recommendation sequences remain unchanged.
The reserved verification task is not used here.

## Reproduction and change

After a worker's first patch, independent testing finds the boundary bug. The
next synthetic assessment confidently recommends returning to that worker and
also reports `needsTesting: 0.99`. Both values are retained exactly.

Previously, the high testing score entered the validation-priority rule. That
rule saw a failed check and selected `ASK_USER`, even though the recommendation
already named a useful repair action and the independent failure supplied the
needed diagnostic evidence. An operator had to select the worker manually or
provide unnecessary clarification to advance that recommendation.

Policy now offers the recommended worker candidate for separate approval when:

- The action probability and reported confidence clear the existing thresholds.
- Linked-task preparation is complete, repository inspection is available, and
  missing-information/stuck assessments do not require operator input.
- The recommendation names the same worker as the preceding implementation
  attempt, that worker is allowed for the run, and a call remains available.
- Required validation is failed, and a failed independent check in the current
  generation was recorded after that worker attempt and before this evaluation.
  Known omission of task validation requirements still requires clarification.

Worker text, earlier-generation results, and a failure recorded before the
worker cannot establish this exception. With no fresh independent check, the
existing testing requirement remains. Other worker choices gain no new route.

The original recommendation, confidence, and testing score are unchanged. The
operator still approves the resolved candidate. Final enforcement continues to
check worker selection, network settings, repeated failures, preparation, and
call limits. Every repair starts a new validation generation; completion still
requires passing independent checks and a separately approved acceptance review.
Decision JSON v1 and orchestration trace schema v2 are unchanged.

## Offline evidence

The regression was run before the policy change. Both focused policy cases
selected `ASK_USER` instead of the requested worker. The targeted workflow
variants stopped at iteration 5 after one worker and one failed independent
check, leaving the boundary bug in place. The test operator stops on an
unexpected `ASK_USER`; it does not fabricate clarification or silently choose
an alternative to hide the detour.

With the candidate, all six provider/model routes and both workers follow:

| Iteration | Approved candidate | Independent evidence |
| --- | --- | --- |
| 1 | `READ_ISSUE` | Exact fixture issue and acceptance criteria. |
| 2 | `READ_FILE` | Root `AGENTS.md` instructions. |
| 3 | Selected worker | First bounded patch; validation generation 1. |
| 4 | `RUN_TESTS` | Actual Node boundary assertion fails. |
| 5 | Same worker | Receives bounded assertion evidence; validation generation 2. |
| 6 | `RUN_TESTS` | Fresh test passes. |
| 7 | `RUN_TESTS` | Fresh lint passes. |
| 8 | `FINISH` | Separate task acceptance approval. |

Each of the 12 variants completes within eight iterations using two worker
calls, three independent checks, eight action approvals, and zero manual
alternatives. The original 183 baseline cases remain alongside these variants;
the workflow file now contains 195 tests. These are scripted enforcement
results, not live routing frequencies or evidence of improved model judgment.

Focused policy cases preserve low/missing confidence, missing context, stuck,
worker selection, exhausted calls, inspection failure, stale/pre-worker checks,
worker-only claims, and premature completion. Loop tests stop, reject, or
interrupt the new repair review without executing it. They also reject approval
when call limits, worker selection, or network settings change during review,
while retaining the first patch and failed validation evidence.

## Other routing investigations

| Area | Evidence and disposition |
| --- | --- |
| Repeated preparation reads | Existing safe instruction-alias and linked-preparation regressions pass. No additional deterministic failure was reproduced. |
| First worker after preparation | Existing policy and workflow cases permit a confident first worker before baseline testing, including a high testing score. Keep that exception and its guards. |
| Redundant tests | Current-generation coverage continues to suppress redundant test candidates and require explicit acceptance review. |
| Diagnosis/repair after a failed check | The mixed repair/testing assessment above reproduced a policy-owned detour and is the only changed routing rule. |
| Completion against current state | Original generation, omitted-check, confidence, missing-information, and acceptance guards remain covered. |

No snapshot construction, question criteria, response normalization, thresholds,
or worker permissions are changed. Remaining hypotheses about live preparation,
worker selection, abstention, or repeated recommendations need observations
under the separately budgeted comparison in step 4. Freeze the accepted
candidate revision before using the reserved task.
