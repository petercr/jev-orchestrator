# v0.6 live stop/resume pilot protocol

This protocol prepares the release gate in PLAN.md after PR #70. It authorizes
preparation and offline verification only. Live collection requires the
operator's explicit approval of the frozen candidate and the bounds below.
Publication requires a later decision after the results and remaining limits
are reviewed. This is a small functional pilot, not a routing-reliability,
performance, or cost comparison.

branch based on merge `1801d78d54b5fd4312fe0ce950e5e9a2786d2a29`.

## Order, scenarios, and limits

| Task | Presentation | Worker | Required observation |
| --- | --- | --- | --- |
| r01 | styled, 80 columns | Codex | Stop at the first post-worker approval before validation; inspect history; resume in a new process and complete with fresh checks and task acceptance. |
| r02 | plain, 80 columns | Claude | The same stop/history/resume workflow with the other worker and presentation mode. |
| r03 | styled, 80 columns | Codex | Interrupt an active worker after its first observed task-file edit; preserve partial edits, charge the call, drain the process tree, then resume and independently validate before any necessary repair and acceptance. |

Freeze six process slots in this order: r01 start/resume, r02 start/resume,
r03 start/resume. There are at most three saved tasks, six CLI launches,
twenty-four evaluation attempts, and six coding-worker attempts in total.
Each task retains the production eight-iteration ceiling and two calls to its
selected worker across both processes. Excluded-worker budgets cannot transfer.
Each CLI process has a five-minute wall limit; the cohort has a thirty-minute
wall limit from its first launch, including time between segments. A limit
interrupts the actual CLI through SIGINT and records cleanup or uncertainty.
Allow up to fifteen additional seconds to drain cleanup after a wall-limit
signal; a forced coordinator exit remains uncertain and blocks continuation.

These request and time bounds limit service use. This client cannot enforce or
report a reliable aggregate dollar charge across subscriptions and providers;
there is no claimed dollar cap. Do not estimate missing usage or cost. No
extra probes, replacement runs, automatic retries, or additional resume slots
are allowed. Any new collection requires an explicit recorded amendment.

On the already documented rejected distribution total or a transient timeout,
network, rate-limit, or server failure, review the actual allowlisted diagnostic
and explicitly continue within the same remaining iteration budget. Stop on
access/authentication failure or other malformed responses. Retain every
failure, recovery, detour, exhaustion, missed interruption, and deviation.

## Fixtures and approvals

r01 and r02 use identical neutral tag-parser fixtures in fresh Git worktrees
with spaces and Unicode paths. Inputs are strings. Split on commas, trim each
part, remove empty entries and duplicates, and preserve first occurrence and
case. Required examples: `a,b` yields `[a,b]`; ` a, ,b,a,, ` yields `[a,b]`;
empty input yields `[]`; `A,a,A` yields `[A,a]`. Edit only `tags.mjs` and
`tags.test.mjs`; preserve package scripts, lockfiles, and instructions.

r03 uses six small modules `step-01.mjs` through `step-06.mjs`, initially
returning zero. Module N must return its numeric input plus N; the fixed check
asserts inputs -2, 0, and 7 for every module. The first worker edit operation
must change only `step-01.mjs`; later edits implement the remaining modules.
The observer sends SIGINT only after it observes a changed allowed file and
an active Codex descendant of this CLI. Record the observed hashes, PIDs,
signal time, and post-exit liveness checks. A missed window or ignored staging
instruction is a retained deviation; do not inject an edit or rerun it.

All fixtures require an approved instruction read and fresh independent
`npm test` after every worker attempt. The worker implements only. The single
fixed test script checks the task's examples without dependencies; original
requirements cannot be dropped after restart. Keep acceptance oracles outside
worker-writable repositories as additional reporting evidence. They cannot
substitute for the CLI's separately approved current-generation validation.

Review every real candidate. At ambiguity, select the offered worker only
when the original task and current evidence justify implementation, then
separately approve the resolved candidate. Resume review grants no action
approval. Compare original task, HEAD, patch hashes, immutable selections,
consumed calls and next iteration, and required fresh reads/checks before
typing continue. Do not change task context, budgets, confidence, permissions,
or worker selection to obtain a route. A repair still needs the policy's fresh
failed independent check and a separate worker approval.

Before FINISH, inspect allowed scope and original behavioral examples, confirm
fresh independent validation in the saved state/ledger and approved trace
receipts, then review and approve resolved task acceptance. Report a valid patch
separately from a completed loop. Finished/exhausted records remain inspection
only. The instrument records observations and never answers a CLI prompt.
