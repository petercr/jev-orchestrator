# Issue #61: explicit recovery mitigation candidate

The candidate verifies bounded, explicitly approved recovery while keeping
malformed responses rejected. It does **not** fix TypeSafe's probability
output. All three newly recorded live runs completed; one natural rejection
required recovery. The operator accepted this release tradeoff on 2026-10-22
and asked to continue. [#61](https://github.com/petercr/jev-orchestrator/issues/61) is resolved
for v0.5 through that accepted mitigation. Merge PR #63 and recheck the
retained candidate against main before publication.

## Proposed release mitigation

Keep the 0.001 sum tolerance, unchanged probabilities and confidence, and no
automatic retries of malformed responses. In orchestration mode, the operator
can review a rejected total and explicitly request another evaluation within
the remaining eight iterations. Each failure consumes an iteration. Recovery
preserves edits, evidence, worker call budgets, the bound provider/model, and
worker/network permissions; it never approves the rejected action. Every
subsequent action and task acceptance still requires its own approval.

This recovery behavior already existed. The production change is clearer
recovery guidance, including that another evaluation may fail. README and
release notes now disclose the observed TypeSafe limitation and distinguish
orchestration recovery from decision-only errors. The first pilot's artificial
one-recovery study cap is absent from this new protocol; removing that study
cap does not change production behavior or demonstrate better router quality.

Residual risk: repeated invalid answers can exhaust a run before acceptance,
even with a correct patch and passing checks. Stopping preserves changes and
diagnostics, returns failure, and does not accept the task. A new invocation
starts a separate run with new approvals; traces cannot resume execution.
There is no automatic provider/model/worker switch or networking escalation.
An operator who requires the provider to always meet the strict contract
should keep publication blocked pending an upstream fix.

## Limits and release decision

Only one natural rejection occurred in this new cohort. Repeated recovery
**was not exercised live here**; the consecutive-rejection path is verified
by the deterministic regressions. The [original mixed pilot](v0.5-live-results.md)
retains four rejections and a stopped run, and the earlier six-evaluation
probe remains separate. This small new cohort establishes neither a failure
rate nor improved routing reliability. It reruns tag parsing, not the staged
repair, linked issues, other live providers, native Windows workers, or real
active-worker interruption.

Evidence is retained outside Git under
`/home/peterc/.cache/dev-issue61-mitigation-20261022`: frozen inputs and hashes,
archive and fresh consumer, exact launcher, process and terminal records,
traces, original-example inspections, full patches including new tests,
validation receipts, results, audits, and installed/terminal verification.
No rejected provider body or credential value is retained.

Accepting this mitigation means accepting occasional failed evaluations and
possible budget exhaustion as a documented v0.5 limitation while preserving
strict rejection and manual recovery. It is not acceptance of approximate
probability totals. The operator explicitly accepted that tradeoff on
2026-10-22 after the proposal and verification were presented, then asked to
continue. PR #62 had
earlier caused GitHub to close #61 because its negated closing phrase still
matched GitHub's closing-keyword syntax; that early closure did not establish
a fix or release acceptance. This later acceptance resolves the release
blocker through mitigation, with all original failures and limitations
retained. Merge PR #63 and recheck the retained candidate against merged
inputs before publication.
