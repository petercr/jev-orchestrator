# Issue #61: distribution precision investigation

This records the initial investigation for
[issue #61](https://github.com/petercr/jev-orchestrator/issues/61), before the
operator accepted the later recovery mitigation. The investigation found a
compatibility gap
between the provider's approximate-total contract and this repository's strict
sum requirement. It has not established a supported precision setting, a
successful mitigation, or the provider's internal cause. That investigation
changed no production behavior, tolerance, model default, or recovery limit.

Follow-up: a separately recorded [recovery mitigation candidate](v0.5-routing-mitigation-results.md)
adds clearer recovery explanations and verifies the existing bounded manual
path. Its new live cohort and installed archive are separate from the

## What the retained evidence establishes

The [original pilot](v0.5-live-results.md) retains four `distribution/sum`
rejections in 26 evaluations, with totals near 0.99. Those failures occurred
on direct TypeSafe REST. The provider and SDK layers must be distinguished:

- [evaluateNative](../../src/ai/native.ts) sends the request through `fetch`,
  bounds the response, parses JSON with duplicate-key rejection, then calls
  `normalizeAssessment`. No TypeSafe or Vercel SDK handles that route.
- [normalizeAssessment](../../src/ai/contract.ts) checks action names and
  finite values, copies each probability unchanged, adds the received values,
  and rejects totals outside 0.001. It does not round or renormalize them.
- The approximately 0.01 discrepancy is materially larger than ordinary
  floating-point summation error for nine bounded numbers. The retained
  diagnostic therefore identifies received values incompatible with our sum
  requirement, rather than a display-only rounding of a valid total.
- Full failed response bodies were deliberately not retained. Their exact
  distributions, served-model identity, and the upstream implementation that
  generated them remain unavailable. Quantization is a plausible explanation,
  not a demonstrated provider-internal cause.

The published [TypeSafe OpenAPI schema](https://api.typesafe.ai/openapi.json)
describes Choice probabilities as summing approximately to one. Its request
properties are `model`, `state`, `questions`, and `assets`; it documents no
probability-precision control. The official
[JavaScript SDK source](https://github.com/typesafe-ai/typesafe-sdk-js/tree/b844cd1aca12855a5d24a2df52a1401c86e7d37a/src)
also exposes no dedicated precision option at the inspected revision.
This does not establish that an undocumented server option exists or works.

The current [models documentation](https://docs.typesafe.ai/models) recommends
version pinning for repeatability. A pin cannot by itself guarantee compliance
with a stronger probability-sum contract. The previous
[v0.4 live pilot](../workflows/v0.4-live-results-v1.md) also recorded invalid
totals while successful evaluations reported `jev-1.13.0`.

## Separate bounded read-only probe

Before calling the service, freeze a new six-evaluation protocol: two synthetic
workflow snapshots (before and after an instruction read), each evaluated with
`jev-latest`, `jev-1.14.0`, and `jev-1.13.0`. The snapshots are diagnostic data;
no orchestration, tools, workers, or saved-run resume are involved. Each model
selection is fixed for its evaluation. The cap is six evaluations and twelve
HTTP attempts, retaining the existing per-evaluation deadline and transient
retry policy. No original pilot observation is replaced.

Collection on 2026-10-22, 17:24:51–17:24:53 UTC used the unchanged native
integration with a read-only observer that compares parsed wire probabilities
to the integration's returned probabilities. The bounded response bytes are
passed through unchanged; bodies and individual probabilities are not saved.
Only successful attribution, an unchanged-values flag, or existing allowlisted
failure diagnostics may be retained. A rejected sum would additionally be
checked against the wire sum in memory.

| Requested model | Before read | After read | Served model on successful evaluations |
| --- | --- | --- | --- |
| `jev-latest` | normalized, unchanged | normalized, unchanged | `jev-1.14.0` |

All six evaluations completed in six HTTP attempts. No worker or repository
action ran, and no result was replaced. This small probe did not reproduce the

## Initial investigation boundary

The existing 0.001 tolerance and malformed-response rejection remain required
by [AGENTS.md](../../AGENTS.md) and #61. Automatically accepting approximate
totals, renormalizing probabilities, retrying invalid responses silently, or
switching provider/model mid-run would not satisfy those requirements.
Current explicit in-process recovery remains available within the existing
iteration budget; it has not been established as an accepted release
mitigation. The original pilot's one-recovery cap was a study rule, not a new
production recovery limit.

An upstream precision clarification/report has been prepared locally; sending
it requires the operator's explicit authorization to contact an external
project. At the end of this initial investigation, a supported provider fix
or explicitly accepted, verified mitigation was still required. The later
mitigation report records those deterministic, live, and installed-package
checks and the operator's acceptance. That later acceptance resolves the
release blocker; this initial investigation alone did not establish a fix.
